# Почему в Dictor нет словаря-суфлёра

Короткий ответ: механизм, который подсказывает модели слова **во время**
распознавания, в нашей связке физически не видит кириллицу. Проверено, а не
предположено. Эта заметка существует, чтобы вопрос не возвращался каждые
полгода.

## О чём речь

FluidAudio умеет **CTC vocabulary boosting** (`Documentation/ASR/CustomVocabulary.md`
в самой библиотеке): вы даёте список терминов, и они подставляются в расшифровку
по акустическому совпадению, а не по замене в готовом тексте. Звучит как прямое
решение задачи «имена и названия должны выходить правильно».

Для нашей модели — Parakeet TDT 0.6B v3 — доступен только вариант с **отдельным
CTC-энкодером** `FluidInference/parakeet-ctc-110m-coreml`: +103 МБ на диск,
~+64 МБ памяти и второй проход по всему звуку.

## Что выяснилось

Словарь токенизатора этой модели — 1024 токена, и **ни одного кириллического**:

```bash
curl -sS https://huggingface.co/FluidInference/parakeet-ctc-110m-coreml/resolve/main/tokenizer.json \
  | python3 -c "import json,sys; v=json.load(sys.stdin)['model']['vocab']; \
      print('токенов:', len(v), '· кириллических:', sum(1 for t in v if any('Ѐ'<=c<='ӿ' for c in t)))"
# токенов: 1024 · кириллических: 0
```

Следствие: любое русское слово превращается в цепочку `<unk>`.

```
Мадина  -> [966, 0, 0, 0, 0, 0, 0]
Рустам  -> [966, 0, 0, 0, 0, 0, 0]     ← побайтово то же самое
GitHub  -> [39, 87, 540]               ← латиница токенизируется нормально
```

«Мадина» и «Рустам» для этой модели неразличимы.

Хуже другое. Решение «заменять или не заменять» принимается сравнением двух
акустических оценок — услышанного слова и словарного термина, — и **услышанное
слово токенизируется тем же английским словарём**
(`VocabularyRescorer+TokenEvaluation.swift:89`). На русской речи обе стороны
превращаются в шум, а к словарной добавляется постоянный бонус (3.0–4.5), так
что она выигрывает почти всегда. Стоп-слова, которые сторожат ложные замены,
там тоже английские: «и», «в», «на» не защищены ничем.

То есть на русском языке механизм вырождается в нечёткую замену по написанию,
выглядящую как акустическое распознавание. Это ровно тот класс решений, от
которого набор `LatinTermRestorations` отказывается сознательно — только здесь
он был бы недетерминированным и непроверяемым тестом.

## Что сделано вместо

Падежи в наборе восстановлений: русское окончание из закрытого списка
(`TranscriptCorrector.RUSSIAN_CASE_ENDINGS`) проглатывается вместе с названием,
поэтому «запушил в гитхабе» → «запушил в GitHub». Ноль мегабайт, ноль
миллисекунд, и — в отличие от суфлёра — множество порождаемых форм конечно, его
можно построить целиком и проверить против списка русских слов. Это и делает
самотест `latin-terms`.

## Когда возвращаться к вопросу

Когда выполнится хотя бы одно:

- у FluidAudio появится CTC-энкодер, в чьём `vocab.json` есть кириллица
  (проверяется командой выше);
- появится biasing на самом TDT-декодере: словарь TDT-модели
  (`parakeet_v3_vocab.json`, 8192 токена) кириллицу представляет прекрасно —
  1161 токен с кириллическими символами. Поле `CustomVocabularyTerm.tokenIds`
  описано в библиотеке как вход для такого biasing, но потребителя у него нет
  ни в одной версии.

Проверено на ревизии FluidAudio `313feb4b` (июнь 2026) и на теге `v0.15.5`.
